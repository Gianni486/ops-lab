## 案例一：磁盘写满

**现象**：业务服务报错，写不了日志，应用侧报 `No space left on device`；SSH 上机后 tab 补全、命令执行都开始不正常。

**发现**：`df -h` 一看，根分区 `/` 已经打满。

```
文件系统        容量  已用  可用  已用%  挂载点
/dev/sda3        17G   13G  3.2G   80%  /
devtmpfs        2.0G     0  2.0G    0%  /dev
tmpfs           2.0G     0  2.0G    0%  /dev/shm
tmpfs           2.0G   13M  2.0G    1%  /run
tmpfs           2.0G     0  2.0G    0%  /sys/fs/cgroup
/dev/sdb1       991M  2.6M  922M    1%  /newdisk
/dev/sda1       976M  136M  774M   15%  /boot
.host:/         466G  353G  114G   76%  /mnt/hgfs
tmpfs           394M  8.0K  394M    1%  /run/user/42
tmpfs           394M     0  394M    0%  /run/user/0
```

再查一次时已经从 80% 冲到 100%，可用空间只剩 63M：

```
文件系统        容量  已用  可用  已用%  挂载点
/dev/sda3        17G   16G   63M  100%  /
devtmpfs        2.0G     0  2.0G    0%  /dev
tmpfs           2.0G     0  2.0G    0%  /dev/shm
tmpfs           2.0G   13M  2.0G    1%  /run
tmpfs           2.0G     0  2.0G    0%  /sys/fs/cgroup
/dev/sdb1       991M  2.6M  922M    1%  /newdisk
/dev/sda1       976M  136M  774M   15%  /boot
.host:/         466G  356G  111G   77%  /mnt/hgfs
tmpfs           394M   12K  394M    1%  /run/user/42
tmpfs           394M     0  394M    0%  /run/user/0
```

**排查命令**：

```bash
df -h                                        # ① 定位：确认是 / 分区满了（100%）
df -i                                        # ② 排除：inode 没满，不是海量小文件导致的
du -ah --max-depth=1 / | sort -rh | head     # ③ 下钻：找大头目录
du -ah --max-depth=1 /var/tmp | sort -rh | head   # ④ 定位：揪出具体文件
find /var/tmp -xdev -type f -size +100M -exec ls -lh {} \;
ls -lh /var/tmp/*                            # ⑤ 确认元凶：一个 3.2G 的大文件
rm -f /var/tmp/<大文件>                       # ⑥ 删除
df -h                                        # ⑦ 验证：回落到 80%
```

**根因**：`/var/tmp` 下堆积了一个 **3.2G** 的临时文件——某个脚本导出的临时数据长期没有清理，日积月累把根分区撑满。

**解决**：确认该文件无进程占用后删除，`df -h` 使用率回落到原来的 80%，服务恢复正常。

**学到什么**：

1. **先定位分区，再找文件，不要一上来就删**——先 `df` 确定是哪个分区、是空间满还是 inode 满，再动手；
2. **`df -h` 和 `df -i` 要一起看**——两者相互独立，inode 打满时空间可能还很富裕，只跑一个会漏掉一类故障；
3. **`du` 默认只打印目录，不打印文件**（本次排查卡住的地方）：目录总计显示 3.2G，但列出来的子项全是一堆 8.0K 的 `systemd-private-*` 目录，大文件"消失"了。必须加 `-a` 才会把文件列出来：
   ```bash
   du -ah --max-depth=1 /var/tmp | sort -rh | head
   ```
4. **`ls -lh` 和 `du` 显示的大小可能不一致**——`ls` 看的是文件声明的逻辑大小，`du` 看的是实际占用的磁盘块；稀疏文件（如虚拟机磁盘镜像）会出现 ls 显示 10G、du 只有几十 M 的情况；
5. **删完空间没释放，别急**——说明有进程还攥着已删文件，用 `lsof | grep deleted` 找出进程，`kill` 或用 `echo > 文件` 截断；
6. **`/var/tmp`、`/tmp` 这类临时目录要有清理机制**——CentOS 7 可以用 `systemd-tmpfiles` 或 `tmpwatch` 定期清理，别让临时文件自由生长；
7. **根分区打满会连锁反应**——不只是写不了文件，PAM 认证、SSH 登录、服务启动都可能失败，所以宁可早发现早处理。

**后续预防**：

- 给根分区加使用率告警（超过 80% 就报警，别等 100%）；
- 日志配 `logrotate` 轮转，临时目录配定期清理；
- 排查命令固化成脚本，出事时一键跑：
  ```bash
  df -h && df -i && du -ah --max-depth=1 / | sort -rh | head
  ```
