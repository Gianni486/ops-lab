> 一句话目标：机器出问题了，**去哪儿翻证据、怎么翻得快**。

## 一、两套日志体系并存

CentOS 7 里日志是**两套并行**的，别以为有了 journalctl 就不需要 /var/log。

| 对比项 | journald（用 `journalctl` 查） | 传统 syslog（`/var/log/` 下的文件） |
|--------|------------------------------|-----------------------------------|
| 存哪 | `/run/log/journal`（内存，重启丢）<br>持久需 `/var/log/journal` | `/var/log/*` 各文件，持久 |
| 格式 | **二进制**，不能直接 cat/grep | **纯文本**，随手 cat/grep/awk |
| 谁来写 | systemd 统一接管：服务的 stdout、stderr、syslog 全收 | 各应用自己写文件 |
| 查询方式 | `journalctl` 一条命令多维过滤 | 每个文件单独翻 |
| 代表服务 | systemd 管理的那些服务 | nginx、mysql、Java 应用等自己写日志的程序 |

> 一句话理解：**`/var/log` 是一摞按作者分好的笔记本，journald 是一个带索引的数据库。** 前者随手翻，后者精确查。

### journalctl 方便在哪（面试能说出前 3 条就够）

**1. 一个入口，不用满地找文件**
老办法出问题要先猜：ssh 的日志在哪？nginx 的在哪？—— `/var/log/secure`、`/var/log/nginx/`……新人根本不知道去哪翻。journald 里 `journalctl -u 服务名` 是统一入口，**服务对象是谁就查谁**。

**2. 结构化字段，能精确过滤**
`/var/log` 里每一行都是一坨纯文本，想按服务过滤只能靠 grep（会误抓、会漏抓）。journald 每条日志都带元数据（`_SYSTEMD_UNIT`、`_PID`、优先级、时间戳），过滤是**按字段精确匹配**，不是字符串碰运气。

**3. 时间范围过滤，一行搞定**
老办法要从 messages 里取某个时段，只能 grep 时间戳或 `sed -n` 数行号。journald：`--since "14:00" --until "15:00"`。

**4. 能按「开机次数」回溯**
`-b` 本次开机、`-b -1` 上一次开机。机器夜里崩了自动重启后想查原因，这个能力 /var/log 基本做不到。

**5. 自带生命周期管理**
`--vacuum-size=500M` / `--vacuum-time=7d` 一条命令瘦身；/var/log 得另外配 logrotate。

**6. 和 systemctl 是一条链上的**
`systemctl status` 看到 failed → `journalctl -u xxx` 直接看遗言，思路不用来回切。

### /var/log 为什么还没被淘汰

1. **纯文本，工具链最成熟** —— `grep`/`awk`/`sed` 随手处理，ELK、filebeat 等采集工具直接吃；journald 是二进制，离开 journalctl 没法读。
2. **历史惯性** —— 几十年的脚本、监控、审计合规都建在这上面，不可能一夜改完。
3. **很多程序自己写日志** —— nginx、MySQL、Java 应用直接 `fopen` 写文件，压根不经过 systemd。journald 只能收到它们的 stdout/stderr，**业务日志（如 access.log）在 journald 里根本没有**。
4. **持久化稳** —— CentOS 7 默认 journald 存 `/run/log/journal`（内存），**重启就丢**；/var/log 在磁盘上，是可靠的长期记录。
5. **跨系统通用** —— 非 systemd 的系统（老 CentOS 6、某些容器）没有 journald，但都有 /var/log。

### 实战怎么选

| 场景 | 用哪个 |
|------|--------|
| 服务起不来、崩了、重启过 | `journalctl -u 服务名` |
| 查访问记录、业务日志 | 翻 `/var/log/应用目录/` |
| 不知道问题出在哪 | 先 `journalctl -p err -b` 扫一遍 |
| 要把日志发给别人看 | journalctl 加 `--no-pager` 导出成文件 |

> ⚠️ `/var/log/journal/` 下的文件是**二进制**的，`cat` 出来是乱码、`grep` 也可能漏匹配，**必须用 journalctl 查**。

## 二、journalctl 命令速查

```bash
# 基本
journalctl                          # 看全部（旧的在前，按空格翻页，q 退出）
journalctl -e                       # 直接跳到末尾
journalctl -n 50                    # 只看最后 50 行

# 按服务（最常用）
journalctl -u nginx
journalctl -u nginx -e              # 看末尾（配合 status 排错）

# 实时跟随（tail -f 效果）
journalctl -u nginx -f

# 按时间
journalctl --since today
journalctl --since "2026-09-17 14:00" --until "2026-09-17 15:00"
journalctl --since "1 hour ago"
journalctl --since yesterday

# 按级别（从高到低：emerg 0 alert 1 crit 2 err 3 warning 4 notice 5 info 6 debug 7）
journalctl -p err                   # 错误及以上
journalctl -p err -b                # 本次开机以来的错误

# 按开机次数
journalctl -b                       # 本次启动之后
journalctl -b -1                    # 上一次开机（机器重启过就用它）
journalctl -b -2                    # 上上次

# 内核日志
journalctl -k                       # 等价于 dmesg

# 组合拳（面试/实战高频）
journalctl -u nginx --since "14:00" --until "15:00" -p err
journalctl -u nginx -b -1           # 上次开机时 nginx 为什么挂了

# 占空间与清理
journalctl --disk-usage             # 看日志占了多少
journalctl --vacuum-size=500M       # 缩到 500M 以内
journalctl --vacuum-time=7d         # 只保留最近 7 天
```

## 三、/var/log 关键文件对照表

CentOS 7 / RHEL 系：

| 文件 | 里面是什么 | 什么时候翻它 |
|------|-----------|-------------|
| `/var/log/messages` | 系统主日志（杂事全在这） | 出问题没头绪时的第一站 |
| `/var/log/secure` | 认证、登录、sudo | **SSH 被暴力破解**、登录失败、提权 |
| `/var/log/dmesg` | 内核启动信息 | 硬件、驱动问题（或直接敲 `dmesg`） |
| `/var/log/cron` | 定时任务执行记录 | "计划任务到底跑没跑" |
| `/var/log/boot.log` | 开机启动过程 | 系统启动慢 / 服务起不来 |
| `/var/log/yum.log` | yum 安装卸载记录 | 谁什么时候装了什么包 |
| `/var/log/maillog` | 邮件相关 | 邮件服务排错 |
| `/var/log/audit/audit.log` | SELinux / 审计 | 权限被拒绝又找不到原因时 |

> Ubuntu / Debian 系略有不同：主日志是 `/var/log/syslog`，认证日志是 `/var/log/auth.log`。

## 四、日志轮转 logrotate

**为什么要轮转**：日志一直写、从来不删，总有一天撑爆磁盘 —— 这就是周六实验"故障一：磁盘写满"的真实成因。

### ⚠️ 头号认知误区：logrotate 不是服务

`systemctl status logrotate` 会返回 **Unit not found**。

它不是常驻后台的守护进程（journald、crond 才是），而是一个**被叫一次、干完活就退出**的普通命令，性质跟 `ls` 一样。既然它自己不会动，那"每天自动轮转"从哪来？——**有另一个服务每天定时去敲它**。

### 完整调用链

```
crond（系统里唯一常驻的角色）
  └─ 每天到点 → 执行 /etc/cron.daily/ 下的脚本
       └─ /etc/cron.daily/logrotate   ← 第 8 题第二个问的答案
            └─ /usr/sbin/logrotate /etc/logrotate.conf
                 └─ 主配置里有一行 include /etc/logrotate.d
                      └─ 加载各应用配置 → 判断该不该切 → 动手
```

去虚拟机上 `cat /etc/cron.daily/logrotate` 看一眼，就是一个几行的 shell 脚本。

### 两个配置位置的关系

| 位置 | 角色 |
|------|------|
| `/etc/logrotate.conf` | 主配置：全局默认值（默认 weekly、rotate 4、create 等），末尾一行 `include /etc/logrotate.d` |
| `/etc/logrotate.d/` | 各应用一个文件（nginx、mysql、yum…），由上面的 include 拉进来 |

**实际生效的配置 = 主配置 + d 目录里所有文件**。子配置里没写的字段，继承主配置的默认值。

**为什么要拆成两个地方？** Linux 的通用套路：软件包安装时自己往 `.d` 目录丢一个文件，不用改别人的主配置；卸载时文件跟着走，主配置始终干净。同一套路还有 `/etc/profile.d/`、`/etc/yum.repos.d/`、`/etc/cron.d/` —— 认准一个就认全了。

### 易混点：「每天被调用」不等于「每天都轮转」

cron **每天都会**把 logrotate 拉起来，但 logrotate 会看配置里的 `daily` / `weekly` / `monthly` / `size 100M`，**自己决定这次要不要真的动手**。配的是 weekly，那它每天被叫醒、每 7 天才真正切一次。

> 补一句：CentOS 7 里 `/etc/cron.daily/` 实际由 **anacron** 管，好处是机器关机错过了时间点，开机后会补跑一次（不像纯 cron 直接跳过）。

### 一份典型配置（逐行拆解 = 验收卷第九题答案）

```conf
/var/log/nginx/*.log {      ← 第 0 行：目标是谁（支持通配符 *，可写多行/多个路径）
    daily                   ← 频率：多久切一次
    rotate 14               ← ① 保留几份历史
    compress                ← ② 压缩旧日志
    missingok               ← 日志文件不存在也不报错
    notifempty              ← 空文件不切
    create 0640 nginx nginx ← ③ 切完创建新文件，并指定权限/属主/属组
    sharedscripts           ← 多个日志时脚本只执行一次
    postrotate              ← ④ 一对关键字的开始
        nginx -s reopen
    endscript               ← ④ 一对关键字的结束
}
```

| 字段 | 干什么 | 容易踩的点 |
|------|--------|-----------|
| `daily` | 切的频率。可选 `weekly` / `monthly` / `size 100M` | 每天被 cron 叫醒 ≠ 每天真的切，频率由这个字段定 |
| `rotate N` | 保留 N 份历史。第 N+1 份出现时，**最老那份直接删掉** | `rotate 0` = 不留历史，切完就删 |
| `compress` | 旧日志压成 `.gz`（access.log.2.gz） | 常配 `delaycompress`：延后一轮再压，避开程序还在写刚切出的那份 |
| `missingok` | 文件不存在也不报错 | 不写的话，日志被删过就会刷错误 |
| `notifempty` | 空文件不轮转 | 避免切出一堆 0 字节文件 |
| `create 权限 属主 属组` | 轮转后**新建一个空文件**顶上，并指定权限和属主 | 不加参数也行（`create` 继承原文件权限）；但程序以普通用户跑时权限不对会写不进去 |
| `sharedscripts` | 目标匹配到多个文件时，脚本**只跑一次**而不是每个文件跑一次 | 不写的话 postrotate 会被执行 N 遍 |
| `postrotate` / `endscript` | 一对**成对出现**的关键字，中间写 shell 命令，**在轮转完成后执行** | 这一段就是配 `nginx -s reopen` 的地方，解决"程序还在写旧文件" |

**为什么 postrotate 里要写 `nginx -s reopen`**：logrotate 只是把文件**改了名**，nginx 手里握的是 inode，它照样往改名后的旧文件里写。reopen = 让 nginx 松手、重新按文件名打开一次，从此写进新文件。这就是第 10 题的根因，两题是同一件事。

**还有几个成对关键字**（知道名字即可）：`prerotate/endscript`（轮转**前**执行）、`firstaction/endscript`（所有日志开始前跑一次）、`lastaction/endscript`（全部结束后跑一次）。

**记忆口诀**：多久切 → 留几份 → 要不要压 → 建新文件 → 通知重开。

### 一份典型配置

```conf
/var/log/nginx/*.log {
    daily              # 每天轮转（也可 weekly / monthly / size 100M）
    rotate 14          # 保留 14 份历史，超了最老的被删
    compress           # 压缩旧日志（xxx.log.2.gz）
    delaycompress      # 延后一轮再压（配合 reopen，避免程序还在写就被压）
    missingok          # 日志文件不存在也不报错
    notifempty         # 空文件不轮转
    create 0640 nginx nginx   # 轮转后创建新文件，指定权限和属主
    sharedscripts      # 多个日志只执行一次脚本
    postrotate
        nginx -s reopen      # 通知 nginx 重新打开日志文件
    endscript
}
```

### 常用命令

```bash
logrotate -d /etc/logrotate.conf        # 演练（dry run），只打印不真做
logrotate -f /etc/logrotate.d/nginx     # 强制执行一次
cat /var/lib/logrotate.status           # 看每个日志上次轮转的时间
```

### ⚠️ 最容易踩的坑：轮转了但程序还在写旧文件

**现象**：`xxx.log.1` 每天都在变大，新建的 `xxx.log` 一直是 0 字节。

**根因**：程序（nginx 等）打开文件后，认的是 **inode**，不是文件名。logrotate 只是把文件**改了名**，程序手里的句柄还指向那个 inode，所以照样往改名后的 `xxx.log.1` 里写。

**两种解法**：

| 解法 | 做法 | 特点 |
|------|------|------|
| **通知重开**（推荐） | `postrotate` 里加 `nginx -s reopen`，或用 `kill -USR1 $(cat /run/nginx.pid)` | 无日志丢失，需要程序支持 reopen 信号 |
| **copytruncate** | 配置里加一行 `copytruncate`：先把内容复制成备份，再把原文件**清空**（inode 不变） | 程序无感知；但复制和清空之间有一瞬间隙，可能丢几行 |

## 五、journal 日志撑爆磁盘怎么办

```bash
# 1. 先看占了多少
journalctl --disk-usage

# 2. 安全瘦身（不是 rm -rf！）
journalctl --vacuum-size=500M      # 压到 500M 以内
journalctl --vacuum-time=7d        # 只留最近 7 天

# 3. 永久限制：编辑 /etc/systemd/journald.conf
[Journal]
SystemMaxUse=500M                  # 最大占用
MaxRetentionSec=7day               # 最多保留 7 天

systemctl restart systemd-journald
```

> 别用 `rm -rf /var/log/journal` —— 正在写的句柄被删会导致空间不释放、日志彻底断档。用 vacuum，它是干净地"登记删除"。

## 六、易错点清单

| # | 易错点 | 正确认知 |
|---|--------|---------|
| 1 | 以为 journal 日志能 cat / grep | 是**二进制**，只能 `journalctl` 查 |
| 2 | 不知道 `-f` | `-f` = 实时跟随，就是 `tail -f` 的替代品 |
| 3 | 不知道 `-p err` | 按优先级过滤，`-p err` 只看错误及以上 |
| 4 | 不知道 `-b -1` | 看**上一次开机**的日志，机器重启过后查故障就用它 |
| 5 | 把 CentOS 主日志记成 rsyslog | 主日志是 `/var/log/messages`（`rsyslog` 是服务名） |
| 6 | 不知道内核日志看哪 | `/var/log/dmesg` 或直接敲 `dmesg`、`journalctl -k` |
| 7 | logrotate 的位置 | `/etc/logrotate.conf` + `/etc/logrotate.d/`，由 `/etc/cron.daily/logrotate` 每天跑 |
| 8 | 不知道轮转后要 reopen | 改文件名不影响 inode，必须通知程序重开或加 `copytruncate` |
| 9 | 日志满了直接 rm | 用 `journalctl --vacuum-size` / `--vacuum-time` |
| 10 | **看了视频没敲命令** | 命令类的东西，不敲等于没学 —— 本笔记所有代码块都去虚拟机上跑一遍 |
